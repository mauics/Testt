# Device Tracker — handoff notes

Paste or upload this file together with the project folder into a new chat (or Claude Code session) on the other account so it can continue the work. Memory does not carry over between accounts, so everything it needs to know is here.

## What it is
A self-hosted Windows PC monitoring and repair-tracking system for a computer lab (admin plus technicians). Rooms 201 and 202 are "Computer Center 1" and "Computer Center 2".
- **Agent** (`agent/agent_windows.py`): tray app on each Windows PC. Reports hardware and peripherals to the server every few seconds. Python with psutil, wmi, pywin32, pystray.
- **Server** (`server/server.py`): FastAPI + SQLite + WebSocket. Pushes live updates to the dashboard.
- **Dashboard** (`server/dashboard.html`): single-file vanilla JS. Tabs: Dashboard (landing page), Monitoring System, Repair Tracking, Inventory, Users (admin only).

## Run it

```
cd server
python3 -m venv venv && source venv/bin/activate     # Windows: venv\Scripts\activate
pip install -r requirements.txt
uvicorn server:app --host 0.0.0.0 --port 8000
```
Open http://localhost:8000. Default admin login is `admin` / `admin123` (the dashboard nags until it is changed). ## Dashboard tab (landing page after login, for everyone)
- Tiles: PCs online, needs attention, open tasks, components tracked. Each tile is clickable.
- Notifications: open problem reports, crashed or not-responding PCs, and keyboard/mouse/missing-part/disk alerts.
- Tasks: technicians see their own open tasks; the admin sees all open tasks with the assignee. Click one to open Repair Tracking filtered to that PC.
- Daily report for a chosen month (◀ ▶): tasks assigned, tasks completed, problems reported, PC incidents. It's a hand-drawn SVG (no CDN, so it works offline on the LAN). It has hover and keyboard tooltips and a Table view.
- **Incidents** are a new table, `incidents`, recorded from this update onward. Kinds: unresponsive (formerly crashed: stopped reporting with no clean shutdown), keyboard_lost / mouse_lost (present in the last report, gone now), part_missing (a baseline part newly missing), disk_low (C: reached 75% used). PCs Under Maintenance are skipped. After a server restart the first report is compared with the last stored report, so nothing is double-logged.
- On narrow screens (760px and below) the tab row sits below the fixed Notifications/Settings buttons and scrolls sideways.

## PC status and pinging (2026-11-05)
- Four statuses: **Online** (reporting), **Unresponsive** (no report for 45 s and no clean shutdown — replaced the old "Crashed"), **No signal** (unresponsive AND the agent didn't answer the server's ping: off, unplugged, off the network, or agent not running), **Offline** (shut down cleanly; never pinged). The old 15-second short "unresponsive" step is gone. Defaults at the top of `server.py`: `UNRESPONSIVE_THRESHOLD_SECONDS = 45`, `PING_INTERVAL_SECONDS = 600`, `PING_TIMEOUT_SECONDS = 4` (all three editable from the dashboard, see below), and `DEFAULT_PING_PORT = 8770`.
- **Pinging:** every 10 minutes the server pings every PC except Offline ones, all at once, and it pings straight away when a PC turns Unresponsive. It calls `http://<PC address>:<PING_PORT>/ping` on the agent, which answers with its device ID; an answer from a different PC (the address was reassigned) counts as no answer. A successful ping turns No signal back into Unresponsive (reachable but not reporting). A failed ping never changes an Online PC; instead its details window shows a firewall hint. The details window shows the last ping and has a **Ping now** button (`POST /api/devices/{id}/ping`, any logged-in user). Live results arrive as WebSocket `ping` messages.
- The server now uses its **own clock** for "last seen", so a PC with a wrong clock can't look silent. The PC's address comes from the report connection.
- **Agent:** a small listener on `PING_PORT` (config.toml, default 8770, 0 = off) that only answers `GET /ping`. If a second copy of the agent is running, it logs a warning and the first copy answers. **Installer:** `install_startup.ps1` adds the Windows Firewall rule "Device Tracker agent ping" (TCP PING_PORT, local subnet only); `uninstall_startup.bat` removes it. If the server is on a different subnet from the lab PCs, widen that rule's RemoteAddress.
- Incidents: the kind is now `unresponsive`; older `crashed` rows are counted as Unresponsive in the month data.

## Start the server automatically at boot (2026-11-06)
Both scripts are in `server/`. They create the `venv` and install requirements if it's missing, start the server now, and open the dashboard.
- **Windows:** double-click `install_server_startup.bat` (asks for admin; optional `-Port 8080`, default 8000).
  - Task **DeviceTrackerServer** runs the server at computer startup, hidden, as SYSTEM, restarting it if it stops. Output goes to `server/server.log`.
  - Task **DeviceTrackerDashboard** runs when the installing user logs in: it waits for the server, then opens `http://localhost:8000/` in the default browser.
  - It adds the firewall rule "Device Tracker server" (TCP port, local subnet). It writes `run_server_startup.bat` and `open_dashboard.ps1`.
  - Undo with `uninstall_server_startup.bat`.
- **Linux / Nobara:** `bash install_server_startup.sh [port]` as your normal user (not sudo; it asks for sudo itself).
  - A systemd **user** service `device-tracker` with `Restart=always`, plus `loginctl enable-linger`, so it starts at boot without logging in. A user service is used because SELinux on Fedora/Nobara blocks system services from running a venv in a home folder.
  - An autostart entry `~/.config/autostart/device-tracker-dashboard.desktop` opens the dashboard at desktop login. It opens the port in firewalld if it's running.
  - Logs: `journalctl --user -u device-tracker -f`. Undo with `bash uninstall_server_startup.sh [port]` (linger is left on).
- Don't also start uvicorn by hand while the startup server is running; the port would be taken.
- Testing: the Linux installer and uninstaller were run in a sandbox as a normal user, with systemctl, loginctl, sudo, firewall-cmd and xdg-open faked: the files written, the commands issued, the browser opening after the server answers, a bad port refused, and a path with spaces. Real systemd, SELinux and the Windows scripts (Task Scheduler, firewall) have not been run.

## Rooms (filter buttons on Monitoring System)
- They're stored on the server in the `room_groups` table, so everyone sees the same buttons. The table was seeded once with Computer Center 1 → 201 and Computer Center 2 → 202.
- Only the admin manages them, using the "Manage rooms" button on the right of the search bar: add (button name + the room to look for), edit, or remove. While typing, the form shows which PCs match.
- Matching works as before: the PC's `ROOM` in config.toml must contain the value as a whole word or number ("203" matches "203" and "Room 203", not "2031"). Duplicate names or room values are refused. Changes reach every open dashboard right away.

## Disk almost full (C: drive)
- Server-only feature; the agent already sends `hardware.disk_percent` / `disk_free_gb` for C:. Settings at the top of `server.py`: `DISK_WARN_PERCENT = 75` (75% used = 25% or less free) and `DISK_CLEAR_PERCENT = 73`.
- When a PC crosses 75%: one pop-up with sound goes to everyone logged in (admin and technicians); click it to open the PC. A `disk_low` incident is logged for the graph. It won't alert again until the disk drops below 73% (this stops on/off flapping). PCs Under Maintenance are skipped.
- While it stays at 75% or above: "Disk almost full" shows in Notifications (sidebar and Dashboard) and the PC's disk bar turns amber.
- Only the C: drive is checked. Other drives would need an agent change.

## Roles and rules
- One hidden admin `admin`. Technicians are role `user`, created in the Users tab or with `manage_users.py`. Login tokens are HMAC-signed. Agents authenticate with the `X-API-Key` header.
- **Assigned tasks** (stored in `repair_tickets`): admin assigns a task to a technician. The technician starts it and completes it. Admin can edit, reassign and delete. Technicians cannot reassign.
- **Complete Task form:** "What did you do?" is required. Ticking "A part was replaced" reveals Part Type (pick list built from that PC's last report), Model Before (auto-filled from the report when one part matches), Model After, and "save as new baseline" (auto-ticked when a part is entered). Part type, before and after are ignored if the box is unticked.
- **Part replacement log (replaced 2026-11-07 by CSV Files/Repair Log):** completing a task with a part used to append a row to `server/archive/part-replacements.csv` (append-only, never pruned). If the file is locked (open in Excel) the row goes to `part-replacements-unsaved.csv` instead.

## Known limitations and ideas not built
- Auto-learning can't separate a keyboard and mouse that share a VID/PID; pin them in `config.toml`.
- A keyboard with a mouse interface can raise a wrong "Mouse disconnected" notification. Offered fix: hide the extra interfaces for pinned devices.
- A laptop's built-in keyboard being counted as external was never diagnosed (needs the `[DEBUG] Keyboard` console lines or `diagnose_devices.py` output).
- Sleep or low battery looks like a crash.
- Scale: about 400 PCs gave roughly 190 ms dashboard refresh. Not built: skipping unchanged reports, WAL mode with a shared connection, a trimmed broadcast.
- Report history only shrinks when the Technician uses Save reports with "Delete"; nothing reminds them yet.
- Ideas offered but not requested: CPU/GPU temperatures (see above).
- Editor note: Pylance shows type warnings in `server.py` (missing imports until the venv interpreter is selected; None vs str). They are harmless. Adding `# pyright: basic` at the top silences them.
